# Walkthrough / Architecture

The astatka flight stays an ordinary flight name. What makes it an astatka is the `astatka_packages` rows pointing at it. **Astatka ajratish** writes `expected` packages from the chosen flights' leftovers. The worker then scans parcels in the window. `POST /scan` answers with the package (client, source flight, track codes, weight, taken-away state) without writing. **Tasdiqlash** sends `POST /confirm`, which moves the package into the astatka flight in one transaction: the track codes in `expected_flight_cargos` and the client's `flight_cargos` rows (sent flags reset). The payment row stays on the source flight (owner's choice), and the send paths check `astatka_packages` so sending the astatka does not write a second debt. After that the flight's own photos page and notification page (Yuborish) see the bag like any other flight's cargo. Every moved id and its old value goes into `move_journal`, which `unconfirm` replays backwards.

Frontend: `AstatkaWorkspacePage` holds the modes (work mode, preview, auto-confirm remembered per device; edit mode per visit) and wires three parts. `useAstatkaWorkQueue` is the work mode's state: scans, the offline index, the confirm queue. `WorkPanel` renders it as the five-column rows. `PackagesPreview` is the saved list from `GET /packages`, falling back to the work mode's index when offline. `WorkspaceHeader` holds the window-wide actions. On a desktop the work panel and the list are two columns that scroll separately, so the scan field never leaves the screen; on a phone they stack in one scroll.

Offline: the window downloads `GET /index`, which lists every package and code of this astatka. Scans resolve against that snapshot. Confirms queue with a client-minted idempotency key and drain when the network returns. The queue lives in IndexedDB per flight, so a reload keeps it.

Part 3. The offline base is `GET /index` with `candidates`: everything a scan on the shelf can meet without the server, worded the same way the server answers (`resolveFromIndex` checks this astatka's packages first, then candidates). A code the base does not know waits for the internet as before. The bag window reads `flight_cargos` through the astatka router, so a worker who has `cargo` permissions but not `flights` ones can still see and fix the photo report; it refuses rows already moved into another astatka.
